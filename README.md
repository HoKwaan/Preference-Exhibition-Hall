# 취향 전시관
세 사람의 취향에서, 당신의 다음 취향을 발견하세요.

영화·음악·책 발견 사이트를 함께 소개하는 Git·GitHub 협업 실습 프로젝트입니다.
HTML·CSS·기본 JavaScript만 사용하며 설치, 빌드, 백엔드, 로그인, 데이터베이스가 없습니다.
카테고리별 카드 1개는 **작성 예시이며 팀원의 실제 의견이 아닙니다.**
공통 추천 선반은 팀원들이 직접 채웁니다.

## 실행 방법
저장소를 내려받고 **index.html을 브라우저로 직접 여세요.**
HTML을 수정하고 저장한 뒤 새로고침하면 반영됩니다. 외부 사이트 방문에는 인터넷이 필요합니다.
JavaScript를 끄더라도 카드와 링크는 표시되며 검색·무작위 추천만 사용할 수 없습니다.

## 폴더 구조
```text
├── index.html          # 메인·팀 소개·공통 추천 선반
├── movies.html         # A: 영화
├── music.html          # B: 음악
├── books.html          # C: 책
├── css/style.css       # 공통 디자인·모바일 대응
├── js/main.js          # 검색·무작위 추천
├── favicon.svg         # 전시관 아이콘
├── README.md
└── .github/
    ├── ISSUE_TEMPLATE/site-recommendation.md
    └── pull_request_template.md
```

## 3인 역할 분담
| 담당 | 작업 파일 | 최종 목표 | 리뷰어 |
| --- | --- | --- | --- |
| A | movies.html | 영화 발견 사이트 4개 이상 | B |
| B | music.html | 음악 발견 사이트 4개 이상 | C |
| C | books.html | 책 발견 사이트 4개 이상 | A |

모두 index.html에도 자신의 추천 카드를 추가합니다. 팀원 이름은 실제 이름으로 바꿔도 됩니다.
공통 CSS·JavaScript 변경은 먼저 이슈에서 협의하세요.

## 카드 추가 방법
1. 담당 HTML의 카드 추가 주석을 찾습니다.
2. `<article class="site-card" tabindex="-1">`부터 대응하는 `</article>`까지 복사합니다.
3. 같은 `id="site-list"` 내부에 붙여 넣습니다. 다른 카드 안에 넣지 않습니다.
4. 사이트 이름, 한 줄 소개, 추천 대상, 직접 작성한 추천 이유, 태그 2~3개, 팀원 배지, 공식 주소를 수정합니다.
5. 실제 의견을 작성한 카드에서만 '· 예시', '작성 예시' 표시를 제거합니다.
6. 검색에 쓰이는 `.site-card`, `.site-name`, `.tags` 클래스를 유지합니다. 별도 데이터 파일은 없습니다.
7. 외부 링크의 `target="_blank" rel="noopener noreferrer"`와 '(새 탭)' 안내를 유지합니다.
8. 완성된 카드를 index.html의 `id="shared-recommendations"` 안에도 복사합니다. 첫 카드가 추가되면 빈 선반 안내는 자동으로 숨겨집니다.
9. 두 곳의 내용은 자동 동기화되지 않습니다. 수정할 때 두 HTML을 함께 확인하세요.
10. 담당 페이지의 모든 예시를 실제 추천으로 바꾸었다면 `example-note` 안내도 삭제하거나 수정합니다.

카드에 id를 추가할 필요는 없습니다. 추가한다면 문서 내에서 고유해야 합니다.
메인 주석은 추가 위치 안내이고, 복사 원본은 각 카테고리에 있습니다.
예시 사이트를 유지해도 되지만 직접 확인하고 본인의 의견으로 다시 작성하세요.

## 브랜치와 PR 흐름
- **main**: 최종 결과
- **develop**: 통합
- **feature/***: 개별 작업

**feature 브랜치 → develop 대상 PR → 팀원 리뷰 → 병합 → 최종 main 반영**

아래는 팀이 별도로 원격 저장소와 develop을 준비한 뒤 직접 실행하는 예시입니다.
develop의 최초 생성은 팀 대표가 한 번만 합니다.

```sh
git switch develop
git pull origin develop
git switch -c feature/a-movie-01
# 담당 페이지와 index.html에 사이트 한 곳을 작성하고 확인
git add movies.html index.html
git commit -m "feat: 영화 발견 사이트 한 곳 소개"
git push -u origin feature/a-movie-01
```

GitHub에서 base를 develop, compare를 자신의 feature 브랜치로 정해 PR을 엽니다.
공식 주소, 추천 이유, 확인한 기능과 화면을 템플릿에 작성하고 팀원에게 리뷰를 요청합니다.
수정 요청은 같은 브랜치에 커밋하고, 승인받아 develop에 병합합니다.
다음 작업은 최신 develop에서 새 feature 브랜치를 만들어 시작합니다.
최종적으로 develop → main PR에서 전체 페이지를 점검한 뒤 반영합니다.

### 사이트 하나씩 작은 PR 보내기
한 PR은 사이트 한 곳의 카드와 메인의 동일 카드를 포함합니다.
관련 없는 디자인 변경과 다른 팀원의 수정은 섞지 말고 별도 PR로 분리합니다.

| PR | 각 팀원이 독립적으로 수행할 작업 |
| --- | --- |
| 1 | 예시를 자신의 첫 추천으로 수정 또는 교체하고 메인에 추가 |
| 2 | 두 번째 서로 다른 사이트를 담당 페이지와 메인에 추가 |
| 3 | 세 번째 사이트를 추가하고 태그 검색 확인 |
| 4 | 네 번째 사이트를 추가하고 모바일·키보드·무작위 추천 확인 |

A·B·C가 각자 위 과정을 진행하면 **개인별 PR 4회 이상, 팀 전체 12회 이상**을 연습합니다.
각자 담당 분야에서 서로 다른 사이트 4개 이상을 완성하세요.
그대로 둔 예시 카드는 실제 추천 수에 포함하지 않습니다.

## 공통 index.html 충돌 해결 연습
1. 두 팀원이 같은 develop 시점에서 각자 feature 브랜치를 만듭니다.
2. 공통 영역의 같은 주석 바로 아래에 각자 카드를 추가합니다.
3. 한 PR을 먼저 develop에 병합합니다. 같은 위치의 추가도 자동 병합될 수 있어 충돌이 항상 생기지는 않습니다.
4. 충돌이 없다면 참가자끼리 합의하여 공통 주석 한 줄을 서로 다르게 수정하는 별도 연습을 할 수 있습니다.
5. 나중 PR 작성자는 자신의 feature 브랜치에서 다음을 실행합니다.

```sh
git fetch origin
git merge origin/develop
```

6. index.html의 `<<<<<<<`, `=======`, `>>>>>>>` 표시를 찾습니다.
7. 양쪽의 완전한 article 블록을 모두 남기고 충돌 표시와 중복된 목록 태그를 정리합니다. 주석 문구는 합의하여 정합니다.
8. '현재 변경만 수락'이나 '들어오는 변경만 수락'으로 상대 카드를 지우지 않도록 주의합니다.
9. 브라우저에서 두 카드와 링크가 모두 보존됐는지 확인합니다.

```sh
git add index.html
git commit -m "merge: 공통 추천 선반의 양쪽 카드 유지"
git push
```

리뷰어도 양쪽 카드가 모두 남았는지 확인합니다.
진행 중인 병합을 취소하고 다시 시작하려면 `git merge --abort`를 사용할 수 있습니다.
팀원 작업을 덮어쓰는 강제 push는 사용하지 않습니다.

## 커밋 메시지 예시
- `feat: 영화 발견 사이트 한 곳 소개`
- `feat: 음악 전시관에 두 번째 추천 추가`
- `fix: 책 추천 카드의 공식 주소 수정`
- `style: 모바일 카드 간격 조정`
- `docs: 책 사이트 확인 방법 보완`
- `merge: 공통 추천 선반 충돌 해결`

## 작업 후 확인
- 메인 ↔ 카테고리 이동과 상단 세 개 링크
- 외부 링크의 공식 주소, 새 탭 열기와 rel 속성
- 이름·태그 검색, 공백, 없는 검색어, 검색 지우기
- 검색 결과 안에서 무작위 추천, 결과 0개일 때 버튼 비활성화
- 카드가 1개일 때 같은 카드를 추천하는 것은 정상
- 탭 키 이동, 엔터/스페이스 버튼 실행, 포커스 표시
- 모바일에서 가로 넘침·겹침이 없는지
- 중복 id, 깨진 태그, 남은 충돌 표시가 없는지

## GitHub에서 별도로 설정할 사항
**main 브랜치 보호는 GitHub에서 별도로 설정해야 합니다.**
README나 템플릿만으로 보호가 적용되지 않습니다.
관리자는 저장소 설정의 브랜치 규칙에서 main의 PR 필수, 팀원 승인, 강제 push 제한을 설정하세요.
develop에도 리뷰 규칙을 적용하면 좋습니다.
실제 원격 저장소 생성, push, PR 등록, 브랜치 보호 설정은 이 초기 구현에서 수행하지 않았습니다.
